# Milestone 4.2 — Etsy financial foundation and Summary polish

Base: `00653f6e373c6c17d523290229fdeed65f5ca134`, branch `codex/ui-ux-design-lock`. Scope is receipt total/currency, isolated capture/refresh/backfill and the existing Summary surface. No fees, exchange rates, net revenue, tax reporting or accounting ledger is implemented.

## Source and monetary contract

Official references checked on 2026-10-09:

- [Receipt endpoints](https://developers.etsy.com/documentation/reference/#operation/getShopReceipt): receipt list/detail under `/v3/application/shops/{shop_id}/receipts`, existing `transactions_r` scope, `grandtotal` Money object.
- [Money definitions](https://developers.etsy.com/documentation/essentials/definitions/): integer `amount`, `divisor`, `currency_code`.
- [Rate limits](https://developers.etsy.com/documentation/essentials/rate-limits/): application QPS/QPD and 429 `Retry-After` seconds.
- [Payments](https://developers.etsy.com/documentation/tutorials/payments/): receipt values may be updated after shipping; receipts are not a settlement/fee ledger. Buyer funding currency and payment-account details require different evidence and are out of scope.

Source is the authoritative receipt `grandtotal`, never a listing's current price, sum of items, AI cost or converted value. The currency shown is the original currency **of the persisted receipt Money evidence**. It does not establish the buyer's card/bank funding currency. No broader OAuth scope or parallel token system is added. Existing owned receipt transport, encrypted grants, scope validation, token refresh and connection epoch fences are reused.

`etsy-receipt-finance/v1` accepts nonnegative integers through signed int64 (`9223372036854775807`), uppercase three-letter currency and a positive divisor at most 1,000,000,000. Only divisors with an exact finite decimal expansion of at most nine places are supported (factors 2 and 5). Other divisors are unavailable rather than rounded. Raw Etsy JSON is parsed losslessly using the existing bounded parser: large integer tokens remain exact strings; decimal/exponent/duplicate-key payloads do not silently become rounded money. Direct unsafe JavaScript numeric inputs are rejected.

PostgreSQL stores amount/divisor as bigint; application persistence uses BigInt, and read DTOs carry canonical integer strings. Display uses BigInt quotient/remainder and locale grouping/decimal digits, followed by the source currency code. It preserves source divisor precision (JPY divisor 1, BHD divisor 1000, even divisor 8), including source-verified zero. Money is never converted to Number; no silent rounding or currency conversion occurs. The current application display locale remains en-US, as elsewhere in Orders; the formatter accepts an explicit locale for future locale selection.

## Storage and verification

Migration `0025_far_ironclad.sql` adds only `order_finances` and an exact identity unique constraint on Orders. One financial projection exists per organization/store/order. Composite FK includes organization, store, order UUID and receipt ID; check constraints enforce evidence identity, contract, verification state, exact money and timestamps. Store/receipt identities are rechecked by the trusted capture service. Provenance retains shop, receipt, contract, normalized finance evidence SHA-256, receipt source version, accepted-total version/verification timestamp, first recorded refund-observation timestamp and latest check timestamp. No raw customer response, integration secret or OAuth token is stored in this projection.

States are VERIFIED, MISSING, INVALID or UNCERTAIN. VERIFIED requires a valid Money object, trustworthy receipt update timestamp, paid/completed state and an explicit empty refunds array. Missing timestamp, conflicting timestamp aliases, unknown refunds or unconfirmed payment never imply verified original money. Equal-version conflicting financial evidence becomes UNCERTAIN until a newer unambiguous version arrives. Older evidence cannot overwrite newer evidence; duplicate evidence updates only the last-check time.

**Order Total means the Etsy receipt grandtotal observed in its receipt currency before recorded refund evidence.** Etsy does not supply an immutable historical checkout/settlement ledger through this projection. A later pre-refund receipt update can refresh a total, including Etsy's own adjustments. The application neither promises that a late first observation reconstructs checkout history nor labels it net revenue. An order first encountered with refunds is UNCERTAIN and has no displayed amount; that observed refund history prevents a later empty refund array from falsely proving an original total. Reconstructing such historical totals requires original pre-refund evidence outside this milestone. If a pre-refund verified total already exists, refund observations retain that total permanently; no refund subtraction is performed. Original total evidence and latest source observation remain distinguishable. Existing operational refund classification is never changed by finance refresh. Refund amounts, allocations, final settlement, fees and tax history remain unimplemented.

## Capture and isolation

The existing explicitly authorized controlled Etsy receipt ingestion captures finance in a nested transaction/savepoint after successful purchase ingestion, using the exact persisted order ID and already-read receipt body. No extra Etsy request occurs. A finance storage/validation failure returns an observable FAILED finance result without discarding a valid operational purchase. Membership/shop/grant fence violations still fail closed. Synthetic fixture stores do not become verified Etsy financial sources.

Finance fields are deliberately absent from `ExternalOrder`, purchased snapshots, line snapshots, source fingerprint and customer answers. The finance-only service writes only its financial table. It does not recreate orders/lines/readings, increment customer revisions, invalidate generated output, call generation, mutate queues, change PDFs or change payment/refund state. Normalizer/fingerprint behavior remains unchanged. Generic live sync is still gated by the repository's `UnverifiedLiveIntakeAdapter`; this milestone supports the existing controlled real-receipt path and does not enable a new automatic live importer.

Refresh/backfill verify persisted owner membership and exact store/order identity before HTTP. A single refresh uses one bounded receipt GET (15-second timeout, 1 MB response limit); existing OAuth infrastructure may refresh an expired grant. Store-first locking serializes financial writes and connection epoch is rechecked before persistence. No client-supplied tenant authorization is trusted. Cross-organization and sibling-store data are denied. Authenticated non-owner operators may read financial information only through their existing authorized Order Detail scope, but cannot run finance refresh/backfill.

The bounded Order Detail read returns VERIFIED exact amount/currency or UNAVAILABLE only. It does not fetch Etsy or trigger backfill. No N+1 reading queries or whole-store history are introduced. Optional financial-table failures degrade to UNAVAILABLE after ordinary order authorization; membership/order failures continue to fail closed. Transport errors retain existing verified evidence and return safe codes, not raw API/SQL/secret-bearing errors.

## Manual refresh and historical backfill

No action runs automatically on deployment, startup, page load, worker tick or sample preview. The explicit operator entry point is `scripts/etsy-finance.ts`, using the repository's existing tsx/env conventions. Do not run against production without intentionally selecting the authorized owner/store and reviewing the batch.

1. Apply the reviewed schema using the existing `pnpm db:migrate` procedure against the intended database. Migration was tested in isolated PGlite, **not applied to the connected/live database during implementation**.
2. Use an existing persisted owner user ID, internal Store UUID and connected matching Etsy grant with `transactions_r`. Missing/expired/revoked authorization requires the existing reconnect flow; no broader scope is requested.
3. Refresh one existing order UUID:
   `pnpm exec tsx --env-file=.env.local scripts/etsy-finance.ts refresh <owner-user-id> <store-uuid> <order-uuid>`
4. Start one keyset batch of 1–20 existing owned orders (default 10):
   `pnpm exec tsx --env-file=.env.local scripts/etsy-finance.ts backfill <owner-user-id> <store-uuid> 10`
5. Read the JSON `results`, `next`, `done`, `stopped` and `retryAfterSeconds`. Resume only if needed:
   `pnpm exec tsx --env-file=.env.local scripts/etsy-finance.ts backfill <owner-user-id> <store-uuid> 10 <next-order-uuid>`

Orders are selected by stable internal UUID keyset, maximum batch+1 rows and sequential GETs, with no unbounded auto-loop. The cursor advances only past terminal outcomes (OK, missing receipt, invalid source). Rate limit, authorization or temporary/DB failure stops the batch before advancing the failing order. Retry resumes from the last successful cursor; null `next` means retry the initial batch. A repeated command is safe and does not duplicate finance records. Invalid source/missing receipts are observable terminal outcomes for a batch; retry a specific order later if corrected. Newly inserted orders behind a prior UUID cursor require a new pass; this is bounded resumability, not a full snapshot scanner.

On 429, **wait at least the reported `retryAfterSeconds` before manually retrying** (60 seconds conservative fallback when absent). There is no automatic retry, sleep, new worker or durable cross-process global rate limiter. Operators must coordinate invocations and respect Etsy's application QPS/QPD budget; do not launch concurrent backfills across stores. This controlled manual mechanism does not claim production-wide quota orchestration. HTTP 401/403 yields AUTHORIZATION; 404 MISSING_RECEIPT; malformed/linkage/response-bound evidence INVALID_SOURCE; timeout/other API or DB failure TEMPORARY_FAILURE. Ordinary Orders workflows remain usable.

## Summary presentation

The locked hierarchy remains Header → Summary → conditional Action Required → Purchased Readings. Only Summary is refined. Total Readings, Generated, Needs Attention, Payment Status and Order Total share a consistent 18px semibold value, muted 12px label, 20px SVG and 1.7 stroke. Desktop auto-fit distributes metrics evenly; tablet wraps predictably; mobile uses two columns, with the fifth financial metric spanning the row for readable exact amounts, wrapping values/labels and no fixed amount width. Long exact values remain readable instead of truncated. Paid uses the same value scale as counts, avoiding disproportionate emphasis.

Purchase Information and Activity remain inside Summary as balanced bordered secondary controls, 44px targets, consistent 20px SVGs, hover and keyboard focus. Their native accessible dialogs, original/current evidence distinction and partial-activity disclosure are unchanged. Existing reading grouping, input editor, preparation, review, PDFs, list navigation and return context are untouched. No emoji or second icon library is introduced; Wallet extends the existing handwritten SVG system.

Verified amount shows exact currency code, e.g. `24.99 USD`. Missing, invalid or uncertain money shows neutral `Amount unavailable`, never a fabricated zero or a technical error. All 50 deterministic sample IDs/guards remain; no sample amounts are added, and sample Summary deliberately omits Order Total even if a finance value were accidentally supplied. Sample routes never import the finance service or execute refresh/backfill.
