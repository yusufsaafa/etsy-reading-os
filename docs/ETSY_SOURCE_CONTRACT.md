# Etsy purchased source and approved mapping — Part 4

Implemented 2026-10-07 from d73d7a4e04a4d87fc618805463443d193a18e00e. This is an internal domain boundary, not a raw Etsy HTTP normalizer, live adapter or real-intake acceptance. Contract authority and unresolved encodings remain the Part 3 matrix in ETSY_REAL_ACCEPTANCE_REPORT.md. No fresh contract assumptions were imported from old MRH code.

Reading OS must adapt to existing seller Etsy listings through explicit mapping whenever the Etsy contract provides sufficient stable source identity; sellers must not be required to rename, reorder, recreate or reclassify listings merely to conform to Reading OS terminology.

## Purchased evidence

`modules/etsy/source-contract.ts` owns strict `etsy-purchased-line/v1`. All nested objects reject unknown fields. Optional source fields use tagged `presence: absent | null | value`, preserving differences instead of inventing defaults. IDs remain bounded opaque numeric strings; source timestamps/money are safe integers. This contract is not lossless arbitrary raw JSON: verified relevant evidence is retained, while unsupported structures must be rejected or represented by a bounded explicit unsupported condition. The future raw adapter must enumerate unsupported fields/types before this boundary, not omit them. That adapter is not implemented here.

| Boundary | Retained evidence |
| --- | --- |
| Receipt | Shop/receipt identity, observation time, creation/update timestamp presence, exact isPaid/status evidence, cancellation state/basis, bounded refund money/status/time and reason presence, separate conservative refund assessment. Refund reason content is intentionally excluded. No buyer identity/address/email. |
| Transaction | Transaction/receipt/listing identity and presence, quantity, optional/null SKU, exact isDigital, listingType and explicit PURCHASE_PINNED/CURRENT_LISTING_OBSERVATION/UNAVAILABLE provenance. A current listing classification is not relabeled as purchase-time evidence. |
| Purchase selections | Property identity, value-ID array presence, formatted name/value evidence, source position and multiplicity. Identity is the property/value set, not position/name/SKU. |
| Buyer content | Original question/property/value identity presence, source type if available, TEXT/UNRESOLVED_DROPDOWN/UNKNOWN encoding, independent answer value presence, display name and optional bounded definition evidence. UNKNOWN retains valuePresence only, without a raw value. |
| Buyer files | Explicit UNRESOLVED state, question/property/type/MIME metadata, source position, answer presence, optional observed file count and definition provenance. There is no URL or download capability. No invented file ID, label association or verified file grouping. |
| Unsupported | Fixed condition codes, optional source position/type and bounded field names. No arbitrary values/raw object. Any condition holds. Unknown input discriminator, source identifiers and value presence are retained; unknown raw values are deliberately excluded because they might be future upload URLs. The contract rejects them rather than stripping them. |

Envelope limit is128KiB UTF-8 serialized; collections cap at3 purchase dimensions,5 content questions,10 unresolved file observations,30 unsupported conditions,100 refund observations. Values/text/instructions cap at10,000 characters; display evidence at500. Source positions are0–127 and distinct across represented entries; they are evidence, never identity. Definition options cap at30, with nullable/absent option identity. These are implementation limits, not additional universal Etsy guarantees. Excess/unknown evidence must lead to a controlled hold/rejection; no truncation or silent omission. The future adapter still needs bounded response parsing before constructing the envelope.

The optional `etsySource` field in the existing canonical line contract is strictly validated. Receipt/transaction/listing/quantity/isDigital and canonical selection-key projections must agree. Raw receipt linkage is checked. Existing owned order/line snapshots retain the typed envelope without new columns or a JSON dumping ground. The intake transaction additionally verifies source shop identity against the owned Store before writes. Only isolated synthetic DB tests exercise that path in this milestone.

## Owner-approved Product policy

ProductVersion gains optional strict `etsyFulfillment: etsy-product-policy/v1`:

- Explicit `fulfillment: READING`, exact listing ID and complete purchase property/value identity set.
- Exact original question ID + property54 + approved text_input semantics → seller InputDefinition key.
- No global tier/speed synonyms, semantic label parsing, SKU fallback, option index, regex rules or model call.

InputDefinition remains the generic seller-domain TEXT/LONG_TEXT/DATE abstraction. Current mapping only supports verified purchased text encoding; dropdown option-to-value encoding and files are intentionally unresolved. Generic non-null selected-value evidence cannot be admitted as text. Future supported types require an explicit contract revision and qualifying evidence; do not fabricate a selected option/file shape.

`beginEtsyProductDraft` is a backend owner command under the existing Store lock, creating/reusing a Product and listing_mappings row with canonical `etsy-selection/1:` key derived solely from the full set of property/value IDs. Rows sort IDs only to produce a deterministic key, without assigning meaning. Duplicate properties or value IDs are rejected. Existing composite uniqueness on organization/store/listing/variant prevents duplicate bindings; the key includes all approved dimensions, so uncovered combinations have no default fallback. No UI/HTTP setup route is added. Future setup must obtain verified inventory identities and deliberate seller approval; this backend command is not an inventory validator or an automatic suggestion service.

Draft creation alone is not approval/runtime authority. Existing save/activation commands require owner authorization, expected revision and Store-first locking. Activation validates input keys and exact canonical listing binding before publishing. A canonical binding cannot change listing/selection identity or remove its source policy on edit; a new selection combination requires its own explicit binding. Published policy lives inside existing immutable ProductVersion JSONB; SQL published-version triggers protect it against mutation/deletion. Operational pause remains independent. No duplicate mapping table or competing version machine is introduced.

The selected ProductVersion carries all configured behavior: sections/output, MANUAL/ASSISTED, generic STANDARD/EXPRESS/target minutes and source question mapping. Sellers can map any verified identity combination to their own configuration. “Extra” does not mean a global tier; “Hour Same” does not mean EXPRESS until the seller approves the corresponding Product configuration. Future deterministic synonym suggestions may assist setup but must produce drafts for approval; ingestion must never consult a suggestion/model or nearest label.

## Runtime eligibility and history

`assessEtsySource` deterministically evaluates already structured source evidence and an approved policy, projecting individually mapped text answers to configured keys while retaining original evidence separately. It does not parse live JSON or call Etsy. `resolveEtsySourceConfiguration` authorizes Store membership/shop identity, finds the exact canonical owned binding and ACTIVE ProductVersion, validates the configuration, and evaluates inputs. It returns owned version/evidence/projected answers/issues, not a delivery or generation command. New persistence calls it inside the existing Store-locked intake transaction. Returned pure policy data alone is not authorization; server-owned version lookup/activation is required.

Etsy marketplace classification is not Reading OS fulfillment eligibility. Both physical-classified and digital-classified source lines can be eligible through the same explicit Product policy. `isDigital=false` and `listingType=physical` stay unchanged. Unmapped physical AND digital purchases hold. Existing fixture/legacy paths without source policy retain their original not_digital behavior; absence never grants new eligibility. A source policy without required source evidence holds.

Source payment, status, cancellation, refund and context checks remain independent. Raw status casing is preserved; only known status semantics are recognized for eligibility. Unknown/missing cancellation or status holds; canceled/refunded/open/processing cases cannot be made ready by a mapping. Any reported refund is held conservatively. The supported reading policy does not imply shipped, completed Reading OS production or delivered status.

Historical safety has two separate fences:

1. Purchased evidence and question identity are authoritative. Display names do not match answers to fields. Current definition evidence is tagged separately and never supplies replacement question identity. Conflicting definition/question identity holds. Unsupported/unknown/dropdown/file evidence remains held even if a seller correction provides text.
2. New source resolution cannot apply an activation to an earlier purchase. Missing receipt creation time or a timestamp before the activation rounded conservatively up to seconds produces ambiguous_historical_mapping and no version. Historical callers must use the server-retained ProductVersion, including ARCHIVED versions; `history.productVersionId=null` never adopts today's active version. That argument must come from owned durable Reading provenance, not a browser claim. No owner historical adoption/import assignment command is added here.

Existing units keep their SQL-protected ProductVersion and append-only customer revisions on replay. Source-bearing initial context is projected from approved question IDs, not caller-provided answer labels. Later config/question/option renames do not replace it. Changed incoming line evidence retains original snapshots and existing sticky source_changed hold. This conservative drift check may hold a reordered/differently displayed observation even though canonical selection meaning is unchanged; it never changes meaning. Quantity expansion stays per line/unit index, independent of the number of buyer questions; quantity>1 still needs per-unit allocation. MANUAL remains manual; ASSISTED admission semantics and no-auto-delivery behavior remain intact.

## Fail-closed conditions

Existing issue arrays/readiness projection are reused, not a new status system. Additional codes: unmapped_purchase_selection, unknown_buyer_input, unresolved_dropdown, unresolved_upload, ambiguous_historical_mapping, source_evidence_incomplete. Existing unpaid/canceled/refund_review/missing_input/unusable_input/quantity_context/source_changed/mapping_paused/unmapped_listing continue to block. Strict malformed/oversized envelope rejection occurs before persistence; a structurally represented unsupported condition remains available for a later controlled hold. No caller should log raw Zod data/customer evidence.

No schema migration is necessary: optional typed snapshot evidence and version-owned policy fit existing JSONB contracts, ownership FKs, mapping uniqueness, immutable published-version and unit-binding triggers. Historical JSON without these fields remains valid. Source snapshots continue to be preserved by existing transactional insert/replay behavior; this milestone does not add a new SQL snapshot trigger. No production database is migrated.

## Part 5 — verified raw normalization and historical permission

Implemented from 0c117f77e9d91a48839064a350f4168e2d4eaf52 on 2026-10-07. `modules/etsy/raw-normalizer.ts` owns `etsy-raw-receipt/1` (the code's boundary version, not a field invented in Etsy JSON). `rawEtsyReceiptSchema` strictly validates the reviewed receipt/transaction subset. `normalizeEtsyReceipt(body, {verifiedShopId, observedAt})` accepts bounded response text and returns one `etsy-purchased-line/v1` per embedded transaction. It performs no HTTP, Product lookup, ingestion, file access or generation. The future caller must obtain shop identity from the owned connection and enforce HTTP status/content type/read limits before supplying text; this function is not itself authorization or a live adapter. The live gate remains closed.

The explicit projection allowlists the official Part3 ShopReceipt/ShopReceiptTransaction fields: consumed identity/payment/status/refunds/timestamps/transactions and transaction identity/linkage/listing/quantity/SKU/digital/variations/product_data enter strict validation; reviewed unrelated commerce, shipping and buyer identity/address/email fields are deliberately excluded. New top-level or transaction field names reject pending review. Consumed nested objects reject unknown fields; there is no passthrough JSON persistence. A nonempty message_from_buyer is explicitly unsupported and holds, without retaining its value. Nonempty refund reasons are reduced to presence; amounts retain amount/divisor/currency/status/time and remain conservatively held. Neither buyer identity nor raw HTTP JSON is returned.

Parsing is capped at1MiB UTF-8, depth20 and30,000 JSON nodes; duplicate JSON keys reject. Integer lexemes above JS's safe range are preserved as strings BEFORE numeric conversion, then ID schemas validate canonical positive decimal signed-int64 range. Already-decoded unsafe numbers reject rather than being stringified. Decimal/exponent lexical forms cannot round into valid integer fields. Zero listing/receipt/question IDs reject as unusable; property IDs may be zero but cannot form an eligible mapping. Relevant numeric quantities/times/money remain bounded safe integers. Arrays are capped at100 transactions,128 variations,3 product_data rows and100 refunds; smaller Part4 output limits still apply and reject excess without truncation. No parser error should be logged with raw input.

| Raw evidence | Normalized treatment |
| --- | --- |
| Non54 property + value identity, no question/MIME | Purchase selection; retain IDs, display evidence and original variation position. Canonical full-set mapping remains ID-only. Duplicate purchase property identities reject. |
| property54 + original question_id + explicit null value_id and MIME | Verified purchased TEXT encoding, original question/property IDs, name/order and absent/null/value answer. No current definition is invented; sourceType remains absent because the purchased schema does not supply it. |
| Question-linked non-null selected value with explicit null MIME | UNRESOLVED_DROPDOWN; preserve observed identifiers without asserting an official option-ID correspondence. Downstream holds. Missing MIME on otherwise text-like evidence remains UNKNOWN rather than being assumed text. |
| Non-null MIME | UNRESOLVED buyer-file structural evidence; retain MIME/question/property/order/value presence only. Exclude value, URL and invented grouping/file count. No fetch/download capability. |
| Other variation | Explicit unsupported condition at that exact source position, with bounded field names only. No arbitrary value survives. Unknown nested fields reject rather than disappear. |
| product_data | Optional bounded `purchaseProductData` corroboration with its own independent source order and tagged property/name/scale/value-ID/value fields. This additive optional field retains purchased evidence without changing existing envelopes. IDs must corroborate variation identities; disagreement, missing identity and unresolved scale semantics hold, never repair by display text. |
| Receipt status/refunds | Preserve raw status casing and is_paid. Recognize documented status meanings conservatively; unknown/missing status/refunds holds. Explicit fully/partially refunded statuses are retained as source assessments; nonempty refund rows alone do not establish full/partial classification. |

Each source variation produces exactly one positional record among selections/content/files/unsupported. The normalizer checks the complete position set and count before returning; product_data corroboration and receipt-level holds do not consume variation positions. Reordered variations preserve their new source positions but yield the same canonical selection identity/mapped meaning. Duplicate transaction IDs and supplied receipt linkage disagreement reject. Creation/update alias disagreement rejects; null/absence remains explicit. Exact physical/digital is_digital is preserved. Listing type is UNAVAILABLE in receipt-only normalization: false is not fabricated into listing_type=physical, and current listing definitions are not presented as purchased facts. Labels, SKU, array order and Same Hour/Extra/VIP terminology have no behavioral authority.

### Explicit historical adoption

Default remains **from activation forward**. A receipt without a usable creation time or predating the selected active ProductVersion activation is held as ambiguous_historical_mapping. There is no automatic application of today's recipe to an old purchase.

`authorizeHistoricalAdoption` is a strict backend owner command (`etsy-historical-adoption/v1`): command UUID, exact receipt ID, published owned ProductVersion ID and inclusive approved purchaseFrom/purchaseThrough epoch bounds. Organization/Store/actor come from authenticated Scope, not command claims. The version's immutable policy supplies exact listing and canonical complete purchase selection scope. The upper bound must predate that version's activation. Each decision explicitly selects ONE receipt/selection combination; future onboarding can enumerate an owner-approved time boundary and submit selected receipts individually. Bounds alone never authorize an unbounded import. There is no bulk import, seller UI, live receipt discovery or hard-coded MRH exception.

Additive migration0021 creates `etsy_historical_adoptions`: UUID, organization/Store, command ID, receipt/listing/canonical selection key, ProductVersion, authorizing owner, inclusive purchase bounds and immutable DB creation timestamp. No answers/raw payloads/credentials are stored. Composite Store/version FKs preserve ownership; command uniqueness ensures replay, and receipt/listing/selection uniqueness prevents conflicting pins. SQL checks enforce identifiers/key bounds/safe ordered timestamps. The migration trigger rejects every update/delete and requires owner membership, a published owned version with matching listing binding and a pre-activation boundary on insert. Service/trigger locking is Store-first. No existing table/backfill or historical version is rewritten.

Exact command replay returns the same record without another audit event; changed payload/actor for the same command conflicts. A second command for the same receipt/listing/selection is safely rejected by uniqueness, even if a writer bypasses the application lookup. Different approved selection combinations on a mixed cart remain independent. Receipt ownership, exact selection identity and purchase timestamp are verified at later owned resolution; authorizing an external ID is not proof a receipt was fetched.

`resolveEtsySourceConfiguration` consults the durable receipt-scoped pin before the activation fence and loads the exact owned ACTIVE/ARCHIVED ProductVersion. A later activation cannot replace it. All normal source, question provenance, missing input, payment/cancellation/refund, pause, unsupported file/dropdown and quantity-allocation checks still apply. Retained unit history takes precedence and `history.productVersionId=null` remains unresolved: adoption is permission before initial binding, not a bypass to mutate existing SQL-immutable unresolved units. Assigning already-ingested unconfigured units remains separate future work. Historical decisions do not automatically create Orders, Readings, production work or deliveries.

Migration acceptance uses isolated PGlite: fresh application, invalid-row/immutability/uniqueness constraints, prior-history preservation, migrator replay/no-op. This does not extend prior native PostgreSQL acceptance to the new historical command; its Store-lock/duplicate-command race needs controlled native evidence before a production concurrency claim. Test fixtures are synthetic only. Real dropdown/upload grouping/access/expiry, historical edited questions, quantity/mixed-cart/replay and real intake remain OPEN debt. No seller listing changes are required.


## Owned product setup catalog — MVP prerequisite (2026-10-08)

`etsy-setup-catalog/v1` is ephemeral current-listing setup evidence, separate from immutable purchased-line evidence. Owner authorization, selected local listing ownership and a connected `listings_r` grant are required before reads. The normal encrypted vault/refresh path remains server-only. GET listing with `includes=Images` verifies shop ownership before GET inventory with `includes=Listing&show_deleted=false` and GET personalization. The inventory listing echo must agree on listing/shop identity, state and update timestamp. Grant epoch, shop ownership and selection are checked again after reads; draft settlement checks them under the existing Store-first lock. Network reads occur outside database locks. No catalog read creates a Product, mapping or ProductVersion.

The projection contains bounded listing presentation, observation time, supported/unsupported question definitions, exact purchase configurations and controlled READY/BLOCKED reasons. IDs are canonical signed-int64 strings parsed with the existing precision-preserving JSON boundary. Responses are limited to 1 MiB and 15 seconds each; inventory to 100 products, three properties per product, 30 values per property, ten offerings per product and five personalization questions. Oversized, duplicate, incomplete or unknown inventory/question structure blocks rather than truncates. Public primary thumbnails reuse the discovery CDN allowlist; no binaries or arbitrary raw JSON are persisted.

Configurations come only from complete identity sets on actual non-deleted inventory products with enabled, non-deleted positive-quantity offerings. No Cartesian combinations are invented. Duplicate full combinations, inconsistent dimensions, missing value IDs and scaled values block. Dependency property IDs must belong to those dimensions. Existing `selectionKey` canonicalizes complete property/value identities; source order, labels and SKU confer no behavior. Labels remain display evidence only.

MVP question support is identified `text_input` with explicit required state and a character bound of 1–1024. Dropdown/upload/future types remain explicitly unsupported; missing identities, file/options metadata or add-on pricing block safe draft setup. Definitions are current setup evidence and cannot reinterpret historical purchased answers. Separate Etsy reads are not an atomic source snapshot; timestamp/identity checks detect observed drift but do not prove no edit between every request. The explicit draft action rereads current evidence.

The minimal chooser requires an explicit complete configuration choice. A real Etsy listing enters existing `beginEtsyProductDraft`, never legacy `beginListingDraft("default")`. The existing unique listing/configuration binding and Store lock make replay reuse the draft without replacing published versions. The initial policy has empty question mappings: seller-approved customer-field mapping and behavior remain subsequent draft decisions. The onboarding activation action rechecks exact current configuration and question identities; missing mappings cannot be silently guessed. Existing domain activation/immutability checks remain authoritative. No per-option override or semantic precedence system is introduced.

Official authority: [generated OpenAPI](https://www.etsy.com/openapi/generated/oas/3.0.0.json), [reference](https://developers.etsy.com/documentation/reference/), [three inventory dimensions](https://developers.etsy.com/documentation/tutorials/third-variation/), [personalization examples](https://developers.etsy.com/documentation/tutorials/personalization/examples/). Inventory is fetched through its dedicated endpoint, not an unsupported listing association. This accepts setup definitions only, not unverified dropdown/upload purchased encodings.
